Chapter 4: Securing the Front Door: Protecting Agents and Execution Entry Points

Every language model invocation incurs real costs in dollar spend, API rate limits, and processing latency. Allowing an unauthorized request past the perimeter consumes tokens formatting prompts, retrieving vector documents, and calling models, only to fail at a downstream tool check. Securing the front door means placing a Policy Enforcement Point (PEP: an inline boundary mechanism that intercepts requests to enforce access decisions) directly at the agent entry point, querying a Policy Decision Point (PDP: the centralized engine that evaluates access rules and returns authorization verdicts) before prompts are rendered or model endpoints are reached.

The Zero-Token Denial Principle

The Zero-Token Denial Principle states that if a caller lacks the entitlement to invoke an agent or execution graph, exactly zero model tokens must be consumed evaluating that refusal.

Relying on system prompt instructions (e.g., "Decline if the user is not an administrator") violates this principle:

  • Economic and Latency Waste: Rejections still incur serialization overhead, HTTP latency, and input/output token billing.
  • Privilege Escalation Exposure: Unhardened entry points allow unauthenticated or unauthorized callers into the model execution loop, relying purely on conversational steering.

Security Boundary Distinction: The Entry PEP enforces caller identity entitlement (verifying roles, clearance tier, and tenant isolation before invocation). Content-level prompt inspection (e.g. neutralizing jailbreak overrides like "IGNORE ALL PREVIOUS INSTRUCTIONS") is handled upstream by the Ingestion Admission Control Scanner (covered in Chapter 5) and input payload sanitizers (Chapter 9). SecureRunnable intercepts the request completely outside the language model loop, terminating unauthorized callers in sub-millisecond time.

SecureRunnable Interception Lifecycle

Because LangChain agents and chains adhere to LCEL (LangChain Expression Language: a declarative syntax used to compose LangChain primitives into executable chains), SecureRunnable acts as a non-invasive transparent proxy around any Runnable or callable. Upon invocation (invoke, ainvoke, stream), it executes a five-step sequence:

  1. Identity Extraction & Resolution: Resolves SecurityIdentity from config["configurable"]["security_identity"] via IdentityBridge. Missing identities default to anonymous and fail closed.
  2. In-Band Config & Callback Preparation: Automatically injects CONFIG_KEY_SECURITY_IDENTITY, CONFIG_KEY_INVOCATION_PARAMS, and the active sec:pdp_engine into config["configurable"], while appending a SecureCallbackHandler to config["callbacks"] so downstream tool and RAG operations are transparently intercepted without manual callback wiring.
  3. PDP Authorization Evaluation: Submits a standardized PolicyEvaluationRequest tuple (subject, action, resource, context) to the PDP engine to enforce tenant isolation, required roles, and minimum clearance floors. Denials record structured audit events and raise an unchecked AgentAccessDeniedException.
  4. Ambient Context Binding: Sets the verified identity into SecurityContextHolder (with a try/finally block guaranteeing context reset), ensuring thread-local and async task propagation.
  5. Execution & Outbound Boundary: Invokes the underlying runnable, applying optional in-flight PII redaction and declarative violation fallback handling.

The library implements this lifecycle by wrapping the target runnable in an inline evaluation gate that manages ambient context and policy enforcement:

langchain_security_extension/security_adapter_langchain/runnable_guard.py

class SecureRunnable:
    """Transparent proxy enforcing PDP entry authorization prior to runnable execution."""

    def invoke(self, input_data: Any, *args: Any, **kwargs: Any) -> Any:
        config = kwargs.get("config", args[0] if len(args) > 0 else None)

        # 1. Gate entry: evaluate roles, clearance, and tenant against PDP (raises if denied)
        identity = self._evaluate_entry_access(config)

        # 2. Bind ambient caller identity to execution context
        token = SecurityContextHolder.set_identity(identity)
        try:
            # 3. Transparently pass execution to underlying Runnable or agent chain
            return self._runnable.invoke(input_data, config=config)
        finally:
            # 4. Guarantee context cleanup to prevent cross-request leakage
            SecurityContextHolder.reset_identity(token)

Code Hardening: The Decoupled PEP Pattern

To harden your enterprise application, decouple your public agent entry methods from underlying execution logic using the Decoupled PEP Pattern. The public entrypoint acts as the Policy Enforcement Point (PEP) gateway—validating caller RunnableConfig and delegating to self.secured_workflow.invoke()—guaranteeing that LLM prompts, token generation, and downstream tools are only ever reached if the PDP grants permission.

In our reference assistant, this pattern is implemented in app/agents/triage_agent.py across two focused steps:

Step 1: Wrapping Business Logic with SecureRunnable

During agent initialization, wrap your core execution method with SecureRunnable.wrap(), declaring the agent's target name, required roles, minimum clearance, and permitted tenant boundaries:

Multi-Agent Delegation & Context-Preserving Handoff

In enterprise multi-agent workflows, an initial triage agent frequently delegates downstream tasks to specialized execution agents (such as a RemediationAgent). When transitioning between agents, naively invoking the second agent can drop caller identity, invalidate L1 decision cache entries, or lose OpenTelemetry trace IDs.

SecureRunnable.handoff() (and asynchronous ahandoff()) solves this by propagating in-band RunnableConfig across agent boundaries while marking sec:handoff_propagated = True and verifying the target agent's entry entitlements:

Declarative Violation Handler & Error Boundary

When an agent executes tools or secondary runnables within an LCEL graph, policy rejections from within the execution graph shouldn't trigger unhandled application crashes or expose internal stack traces. In your application, bind an error boundary to SecureRunnable using .with_violation_handler(violation_handler, fallback_builder):

Explanation: When a downstream tool execution is blocked by policy, the error boundary catches the exception, resolves the violation details via the ToolViolationHandler, and invokes the fallback_builder to generate a graceful remediation report containing security diagnostic telemetry (e.g., remediation_security: BLOCKED_POLICY, remediation_execution: ABORTED) rather than aborting abruptly.
