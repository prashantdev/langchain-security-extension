Chapter 6: Integrating Your Vector Database: Permission-Aware Search and Data Pruning

Ingesting document chunks with sec:* security envelopes is only half the battle. When a user asks a question, the vector database retriever must ensure that restricted chunks and chunks from other tenants never leak into the model's prompt context. Vector search alone measures only semantic similarity, not authorization. Securing knowledge retrieval requires dynamic query pre-filtering to instruct the database engine to drop unauthorized records, coupled with in-memory post-retrieval verification to discard tampered entries and enforce clearance floors.

Two-Phase Retrieval Architecture

The contextual retrieval filter operates across two deterministic defense stages:

  1. Phase 1: Dynamic Filter Push-Down (Pre-Filtering): Extracts SecurityIdentity from LangChain's RunnableConfig and translates caller attributes into a native vector database filter dictionary (e.g., {"$and": [...]}).
  2. Phase 2: Post-Retrieval Pruning & Verification: Validates retrieved candidate chunks in memory against the caller's clearance floor, role memberships, and cryptographic HMAC signatures before handing documents to the LLM prompt assembler.

Dynamic AST Pre-Filter Translation

An Abstract Syntax Tree (AST: a hierarchical tree representation of structural code or query expressions) dynamically compiles the caller's identity claims into the vector store's native dialect. This offloads coarse access control directly to the database engine:

def build_full_ast(self, identity: Optional[SecurityIdentity]) -> PrefilterAST:
    """Constructs unconstrained full pre-filter AST from caller SecurityIdentity."""
    if identity is None or identity.is_anonymous or identity.subject_id is None or str(identity.subject_id).upper() == ANONYMOUS_SUBJECT_ID:
        # Strict Fail-Closed: Unauthenticated callers receive a synthetic deny-all sentinel filter
        return PrefilterAST({SEC_TENANT_ID: "__DENY_ALL_UNAUTHENTICATED__"})

    and_clauses: List[Dict[str, Any]] = [
        {SEC_TENANT_ID: identity.tenant_id},
        {SEC_CLEARANCE_FLOOR: {"$lte": identity.clearance_level}},
    ]
    if identity.roles:
        and_clauses.append({SEC_ALLOWED_ROLES: {"$in": list(identity.roles)}})
    return PrefilterAST({"$and": and_clauses})

Explanation: If an unauthenticated caller issues a query, the method returns a synthetic deny-all filter (__DENY_ALL_UNAUTHENTICATED__), guaranteeing that no records match. For authenticated callers, it binds their tenant ID, clearance floor, and assigned roles into native database query filters.

Post-Retrieval Pruning, Top-K Oversampling, and In-Flight PII

When databases support only partial filtering or when metadata requires cryptographic verification, chunks must be pruned in memory. If a query requests 5 chunks (K=5) and 4 are discarded during clearance checks, the model suffers from Result Starvation (an information-loss condition where access pruning leaves too few documents for accurate reasoning).

To prevent result starvation, SecureRetriever calculates an inflated candidate fetch size before querying the vector store:

K_fetch = min(K_target × OversamplingFactor, K_max)

If post-retrieval pruning still leaves fewer than K_target chunks, the retriever executes adaptive secondary paging up to a bounded threshold (default: 2 attempts). To prevent irrelevant documents from being injected simply to satisfy K_target, candidate oversampling and secondary paging enforce a configurable similarity score cutoff floor (similarity_cutoff, default: 0.0), discarding any candidate whose similarity score falls below the relevance floor.

Post-retrieval verification also serves as an active in-flight PII enforcement point: when full in-flight sanitization is enabled, retrieved document chunks are intercepted at stage PII_STAGE_RETRIEVAL_DOCUMENT and redacted before entering model prompt context (see Chapter 9: Sanitizing Sensitive Payloads for detailed redaction policies).

Restricted Title Pruning & Telemetry Redaction

When candidate documents are discarded during post-retrieval clearance evaluation, SecureRetriever records the title/header of each unauthorized document into config["configurable"]["sec:pruned_doc_titles"]. Downstream agent telemetry finalizers (such as finalize_telemetry() in app/agents/guardrail_tests_telemetry_helper.py) inspect this list to redact restricted document names from user responses and logs with [REDACTED_RESTRICTED_DOC], preventing indirect data leakage via document titles.

Auditing and Telemetry Events

During query execution and candidate pruning, SecureRetriever emits standardized audit events to the Policy Decision Point (PDP) audit pipeline:

  • EVENT_POLICY_TAMPER_DETECTED (Severity: CRITICAL_ALERT): Emitted when a document chunk's sec:envelope_hash fails cryptographic HMAC verification, dropping the tampered record immediately.
  • EVENT_RAG_UNAUTHORIZED_PRUNING (Severity: NOTICE): Emitted when candidate chunks are pruned in memory due to missing mandatory security envelope tags, insufficient clearance level, or role mismatch.
  • EVENT_RAG_RESULT_STARVATION (Severity: WARNING): Emitted when final authorized candidates returned to the caller are fewer than the requested target top-K despite oversampling and secondary paging attempts.

Vector Store Metadata Type Constraints

Embedded stores like ChromaDB require primitive scalar metadata types (strings, integers, floats, booleans). Complex attributes such as sec:allowed_roles must be flattened into delimited strings during ingestion, and reconstructed during retrieval:

DEMO APP (DIFF) app/agents/knowledge_base_store.py
PYTHON 
def to_chroma_metadata(meta: Dict[str, Any]) -> Dict[str, Any]:
    """Normalizes metadata values into ChromaDB-compatible primitive scalar types."""
    chroma_meta: Dict[str, Any] = {}
    for k, v in meta.items():
        if isinstance(v, (str, int, float, bool)):
            chroma_meta[k] = v
        elif isinstance(v, (list, tuple, set)):
            chroma_meta[k] = ",".join(str(item) for item in v)
        elif v is None:
            chroma_meta[k] = ""
        else:
            chroma_meta[k] = str(v)
    return chroma_meta

Explanation: Complex Python types like lists or sets are flattened into comma-delimited strings to comply with ChromaDB's scalar storage requirements, preserving all security envelope attributes without serialization errors.

Storage Engine Capability Profiles

Vector databases differ in their native filtering capabilities. SecureRetriever negotiates filter predicates based on the underlying storage profile:

Store Capability Profile Database Push-Down (Phase 1) In-Memory Fallback Pruning (Phase 2)
Full AST Profile
(PgVector, OpenSearch)		 Full push-down: tenant_id, numeric clearance_floor (0 ≤ PUBLIC < 1 ≤ INTERNAL < 2 ≤ CONFIDENTIAL < 3 ≤ RESTRICTED), and role set containment ($in). HMAC integrity verification and final top-K window truncation.
Constrained Profile
(Basic / Key-Value Stores)		 Partial push-down: strict equality on sec:tenant_id and optional sec:department_id. Clearance ranking, role intersection, HMAC verification, and secondary page hydration.
No-Filter Profile
(Simple In-Memory Stores)		 None (bypassed). 100% evaluated in memory across all security envelope tags with 3.0× oversampling.

Note on ChromaDB and Embedded Stores: While the demo application specifies STORE_PROFILE_FULL_AST for ChromaDB to evaluate basic equality and numeric ranges, ChromaDB does not natively support array containment on unflattened lists or complex boolean operators like $exists. The security adapter applies _sanitize_chroma_filter() to strip incompatible clauses before query execution, relying on Phase 2 post-retrieval verification to evaluate any unsanitized predicates.
