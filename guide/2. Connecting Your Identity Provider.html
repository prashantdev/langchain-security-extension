Chapter 2: Connecting Your Identity Provider: Passing User Credentials into LangChain

Enterprise applications authenticate callers at the network perimeter using Identity Providers (IdPs) such as Okta, Keycloak, Auth0, or Microsoft Entra ID. Once a perimeter gateway validates a session cookie or JSON Web Token (JWT), downstream AI components must know who initiated the execution. Bridging this identity into LangChain requires an IdentityBridge to extract verified claims, map them into an immutable SecurityIdentity, and inject them into LangChain's native RunnableConfig execution configuration.

Connecting Your Identity Provider at the Perimeter

Before claims reach LangChain, the application or API gateway integrates directly with the corporate Identity Provider via standard OpenID Connect (OIDC) and OAuth 2.0 protocols:

  • OIDC Discovery & JWKS Key Rotation: During startup, the perimeter service fetches the IdP's metadata from /.well-known/openid-configuration to retrieve the JSON Web Key Set (JWKS) endpoint (jwks_uri). Public keys are cached locally and refreshed periodically to handle automated key rotation.
  • Cryptographic Signature Verification: Inbound HTTP requests supply an Authorization: Bearer <token> header. The gateway or framework security filter inspects the token header for the matching key ID (kid), verifies the asymmetric signature (e.g., RS256 or ES256) using the cached public key, and validates token expiration (exp).
  • Standard Claims Validation: The perimeter verifies core standard claims, ensuring the token issuer (iss) matches the trusted IdP authority and the audience (aud) matches the application client identifier.
  • Hand-off to the AI Application: Once cryptographic integrity is established, the raw verified claims dictionary (including subject sub, roles, tenantId, and organizational attributes) is handed to the application's IdentityBridge to be transformed into execution context for LangChain.

The Role of the Identity Bridge

The IdentityBridge serves as the translation layer between web frameworks (such as FastAPI or Flask) and LangChain runtimes:

  • Token & Header Extraction: Extracts verified subject claims and distributed tracing context (such as W3C traceparent headers) from incoming HTTP requests.
  • Claim Normalization: Translates enterprise claims into standardized fields for multi-tenancy, clearance ranks, and RBAC (Role-Based Access Control) groups.
  • Immutable Packaging: Emits an immutable SecurityIdentity that downstream agents and tools cannot alter during execution.
  • Native Context Propagation: Attaches caller context directly to LangChain's RunnableConfig under config["configurable"]["security_identity"], avoiding fragile thread-local storage across asynchronous agent turns.

class SecurityIdentity:
    """Immutable caller identity envelope containing authenticated attributes."""

    def __init__(
        self,
        subject_id: str,
        tenant_id: str,
        roles: Set[str],
        clearance_level: int,
        department_id: str,
        attributes: Dict[str, Any],
    ):
        self._subject_id = subject_id
        self._tenant_id = tenant_id
        self._roles = frozenset(roles)
        self._clearance_level = clearance_level
        self._department_id = department_id
        self._attributes = dict(attributes)
  • subject_id: The primary caller identifier (e.g., the JWT sub claim or corporate email).
  • tenant_id: The organizational boundary key, essential for preventing cross-tenant data leakage.
  • roles: An immutable set of RBAC groups (e.g., {"ROLE_DEVOPS_ENGINEER", "ROLE_USER"}) stored internally as a frozenset.
  • clearance_level: A numeric rank (0 ≤ PUBLIC < 1 ≤ INTERNAL < 2 ≤ CONFIDENTIAL < 3 ≤ RESTRICTED) used for hierarchical vector chunk gating.
  • department_id: Organizational department key used for departmental policy constraints.
  • attributes: Validated operational tags (e.g., distributed trace_id, span_id) consumed by policy rules and audit loggers.

Immutability Guarantee: SecurityIdentity protects caller integrity by encapsulating attributes behind read-only property getters and storing roles within an immutable frozenset. Untrusted model outputs, prompt injections, or child runnables cannot mutate caller attributes or escalate roles during the execution lifecycle.

Role-to-Clearance Rank Mapping (CLEARANCE_RANK_MAP)

Enterprise Identity Providers emit role assignments as arbitrary string values or LDAP/AD group memberships (for example, ROLE_ADMIN, ROLE_DEVOPS_ENGINEER, or ROLE_USER). However, fine-grained access control in LangChain—such as vector database pre-filtering and tool parameter constraints—evaluates hierarchical data classifications using monotonic integer ranks. Example:

0 (PUBLIC / UNAUTHENTICATED) < 1 (STANDARD / INTERNAL) < 2 (SECRET / CONFIDENTIAL) < 3 (TOP_SECRET / RESTRICTED)

To bridge this difference, IdentityBridge.build_identity_from_claims() accepts a clearance_rank_map dictionary (such as CLEARANCE_RANK_MAP). The bridge inspects inbound role claims and resolves the user's active clearance rank by evaluating the maximum rank corresponding to their assigned roles (or applying a configured default_clearance). This normalizes disparate enterprise group naming schemes into consistent numeric clearance tiers across all downstream agents, retrievers, and tools.

Context Propagation via RunnableConfig

Traditional web patterns rely on session cookies or thread-local storage, both of which fail across asynchronous event loops, background worker queues, and multi-agent transfers. LangChain resolves this natively through LCEL (LangChain Expression Language) execution configs. Passing caller context under config["configurable"]["security_identity"] ensures caller identity flows deterministically into every nested prompt, tool call, and vector retriever query without relying on global variables.

During downstream execution, IdentityBridge.resolve_identity() resolves caller context through a deterministic three-tier lookup sequence: it prioritizes an explicit candidate passed in RunnableConfig, falls back to the current async task context via SecurityContextHolder (using Python contextvars), and ultimately defaults to an unprivileged SecurityIdentity.anonymous() (clearance 0, empty roles) to maintain fail-closed security.

Framework Integration & Best Practices

  • Perimeter Cryptographic Validation: Always verify token signatures and expiration timestamps at your gateway or web framework middleware before invoking IdentityBridge. Never construct an identity from unverified claims.
  • Mandatory Multi-Tenancy: Enforce the presence of tenant_id on every incoming request to prevent accidental cross-tenant document and tool access.
  • Explicit Propagation: Always pass config=config to entry points, child runnables, and manual tool calls so caller identity is never dropped mid-execution.
  • Fail-Early Rejection: If a token lacks a valid subject (sub) or tenant identifier, reject the request with HTTP 401/403 immediately before initializing LLM chains or consuming model tokens.
  • Immediate Cache Invalidation on Revocation: Coordinate user role revocation events between your identity directory and the LangChain PDP cache to prevent stale permissions from persisting.
